# 连续一天真实模型评估

本报告评估 `419415ee2f4031446210d908b656f6d07ba27f12` 的连续游戏行为。测试日期为 2026-09-13（上海时间），使用 DeepSeek 官方 API、`deepseek-v4-flash`，以 standard 模式为主、追加 strict 原版开局验证，单次输出上限 40,000 tokens、上下文预算 100,000 tokens。数字以同目录最终数据文件为准。

## 实测结果

共记录 **8 条轨迹、166 次完整尝试、1,196 次请求发起**。其中原版为 **4 条轨迹、27 次尝试、2 次成功提交、360 次请求**，没有一条完成整天。不是 1,196 个独立剧情样本；请求包含各 Agent、修复、后台预规划和结构化重试。调查诊断人工停止时正在进行的下一次尝试未纳入，故请求数是完整留档范围内的计数。

上述延迟用完整提交计时，快速路线包含两次错误空提交；不是每个数字都代表玩家开始阅读。后台也等到稳定的采集运行总时长分别约 3分18秒、16分14秒、14分02秒，不应把与阅读可重叠的后台耗时全部算成阻塞。

若只为理解阅读量，假设每分钟阅读400–700个字符，第一选项路线的已解析正文约需45–80分钟，加前台等待约55–90分钟；静态开局、观察面板、思考和操作时间还没有算入。这是**明确假设下的估算，不是真人计时**。不能把“模型总共等了十分钟”误说成“一天十分钟玩完”。逐项调查尚未完成便已有近四万字符，重复内容会让这种阅读负担更加明显。

已采集请求中1,194次返回HTTP 200，另有1次401与1次TypeError（均在快速诊断的T7记录）。绝大多数剧情失败发生在API正常返回后的审核/解析/提交流程。1,035次响应提供 usage，合计 prompt 6,650,639、completion 486,507 tokens；其余主要为流式请求，缺失usage，所以这不是完整消费账单。最大已报告单请求 prompt 为13,722 tokens，最大完整 messages 序列化长度35,170字符。设置100k预算不等于实际向Writer传了100k，也不能把这里的遗忘与时间错误直接归因于上下文预算耗尽。

完整逐回合时间、正文、选项和审核记录见随附[数据摘要](2026-09-13-live-day-data.json)与[逐回合转录目录](day-evaluation-2026-09-13/)。原始请求证据在工作区 `.codex-test-tmp/day-evaluation/`，未包含API请求头或密钥。

## 方法与口径

测试从真实 `startNewGame()` 静态开局开始，身份为男性李明。实际调用游戏 hook、Director、Writer、审核、修复、State 调度、后台清单和预规划；连续保留聊天、变量、认知和世界记忆。没有用预写模型回答替代 API。仅把聊天落盘隔离，避免污染玩家存档。测试在 jsdom 中推进播放完成标志，未模拟真人阅读速度、鼠标操作、画面和音效；因此是实际模型驱动的游戏逻辑集成测试，不是完整浏览器视觉验收。没有加载用户自定义世界书。

一个“尝试”是一次发送或重试，一个“提交回合”是 history 成功增长，一个“可播回合”还必须有实际台词。模型请求数另计，包含前台生成、修复、结构化重试和后台请求。静态开局、地图本地移动、逐句点击不算模型生成回合。一天完成须真实触发午夜重置，cycleCount 从 1 变为 2；体力或理智耗尽的提前重置另列，不能算过完日历上的一天。

每条路线从独立新游戏开始。失败后先重试一次，继续失败则发送中性下一步输入；连续六次失败停止。该停止规则说明“测试被阻断”，不证明永远无法用其他输入绕过。反复采用同一宽泛输入或第一选项，也不代表所有真人玩家的行为分布。样本用于发现可复现问题，不用于估计全体玩家概率或稳定 p95。

严格分开三类组别：

- **原版**：审核行为完全不改。
- **审核提示校准**：仍实际执行并服从文风审核，只补充“旧文引句必须存在、固定人物特征和授权事实不是天然违规”等说明。
- **文风仅观察**：实际运行原审核并记录结果，但测试包装器不让文风拒绝阻断；确定性文风拒绝也如此。事实、协议和状态流程仍照常。这是用于观察下游的反事实诊断，绝不是生产通关证明或建议直接关闭审核。

快速路线明确要求一次寻找/等待两小时；调查路线依次走便利店、学校、周大爷、护士、山路/旅馆、赵刚、灯织等交互；选项路线选择实际返回的第一选项，检验选项能否持续引导推进。原版和诊断组的输入策略相同，但真实生成具有随机性，不是严格同样本 A/B。部分轨迹并发请求同一供应商，延迟可能受竞争影响。

前台总等待含失败与重试；`playableMs` 原本表示提交时刻，本次发现空场景也会记录该指标，所以不能不检查台词就把它解释为开始阅读。后台收尾时长单列，不能简单全部加到玩家前台等待上。API token usage 只在响应提供时统计，缺失不能视为零。

## 已确认的系统问题

### 1. 正式开局的事实账本与审核历史不一致

正式开局已经提到衣柜、绿色围裙、纸条、手机、饭盒、药瓶与梦等信息，但初始 mysteryKnowledge 没有对应提交。第一次 Director 仍收到空的 playerKnownFacts，并再次分配“衣柜里有一处不自然的空缺”这一低阶段事实。同时，文风历史会把开局嵌套的观察/调查菜单全部当作已经读过的正文。

因此，同一信息可能被规划要求再呈现，被事实审核视为未授权，又被文风审核视为旧文复读。这里既有权限同步问题，也有“候选与旧文”混淆的模型误判。不能把所有失败都归结为 Writer 泄密。

证据位置：`src/engine/opening-storyline.ts:88`、`src/utils/gameSession.ts:23,122`、`src/agents/mystery/turn-preparation.ts:46`、`src/agents/mystery/style-review.ts:113`。实际原版第一条调查轨迹的文风评审，把只存在于候选陈慧慧段落中的“她招呼你的时候嘴角一直往上提着”等句子，说成近期旧文；实际旧文只有静态开局，没有陈慧慧出场。原版快速路线亦有旧文中不存在的引句。源码没有把当前候选加入旧历史，故这是评审错误归属，非代码把候选和自己比较。

`style-review.ts:134` 的确定性检查收到豁免事实，但 `:157` 的语义模型请求没有收到同样豁免。`:172` 只校验违规消息是字符串，没有核验引句确实来自旧文。单纯增加审查说明不能解决整个问题。

### 2. 空场景可以成功提交，并消耗游戏时间

快速“文风仅观察”轨迹 T5、T8 均成功提交但 `lines=[]`。maintext 只剩场景和音乐，剧情被放入 observe，部分还带字面量 `\\n`。T5 将时间从 14:45 推至 16:45，T8 从 17:30 推至 20:00。它们有 protocol、persistence、commit 记录，没有触发修复。T8 的文风审核本身甚至判为通过。

这不是报告漏摘台词：`stream-parser.ts:52` 在遇嵌套新标签时结算旧标签；`output-protocol.ts:75,193` 只要求 maintext 非空且指令合法；`scene-parser.ts:136,220` 允许只含场景/音乐并返回空 lines 的 Scene 对象；`useGameLoop.ts:674,725` 只检验 Scene 对象存在，不检验台词数量，随后持久化和结算。`DialogueBox.tsx:81,186` 的零行完成条件也未形成可靠阻挡。

剧情可能出现在观察面板，但不会作为正常对话场景播放。因此“十次成功提交”不能直接说成“十个正常可玩的剧情回合”，时间上限再合理也不能抵消这个缺陷。

### 3. standard 泛化行动会跳过地点与资源结算

同一快速诊断轨迹的十回合都没有 State 阶段，location 始终 home、体力始终 100、理智始终 70。正文却多次在街口、商住楼屋檐下活动，长时间找人，并收到死亡通知。

原因链条：`orchestrator.ts:515` 仅在 strict、饱和转场或 requiresStateAgent 时调度 State；`turn-preparation.ts:196` 的要求依赖明确行动、已解析目的地或非普通意图。“附近继续寻找”不匹配 `action-narrative-context.ts:34` 的目的地白名单，于是没有确定性旅行成本，也不强制 State。`useGameLoop.ts:990` 使用空补丁结算；`:419` 只有明确目的地契约才保证地点写入。Writer 按设计不能直接写状态。死讯本身也没有被加入强制 State 条件，理智下降目前只有提示要求。

这是“没有调度负责更新状态的环节”，不能表述成 State 模型明知变化却拒绝修改。明确目的地的调查路线确实有旅行扣费，说明问题集中在自由输入解析和调度覆盖，并非所有成本都失效。

### 4. 真实重复与审核误判同时存在

快速诊断 T3/T4 连续重复灯织查看裤脚和手机、把袋子放墙根、劝回家、走台阶再补一句的全过程：

> T3：“回去。换身干的，吃点东西。”“伞别靠在墙上，水会渗进去。”
>
> T4：“回去。换身干的，吃点东西。”“伞别靠墙，水会渗进去。”

T9/T10 又整段近义复写手机送达标记、天气预警、外套、感应灯不灭、轮廓被水泡软、声音隔水、催回公寓与椅脚刮地。这里文风审核的拒绝有真实依据。玩家允许等待，并不等于应该在两个相邻回合重新完整演一遍同样动作。

第一天不能确认真相，facts 为空本身不算错误；但仍可以通过确定已问过谁、排除一个地点、安排可执行下一步、改变关系和兑现约定推进。这些层面的增量也偏少。快速轨迹仅新增 meet:old-man 与 insight:touko-protective，搜索反复得到泛化无果，直到固定死讯触发。体感拖沓不是只由回合数决定：十回合也可以因为每回合重复六七百字而拖沓。

### 5. 修复可能保住协议，却破坏对话衔接

调查诊断 T8 有“你说吃过了”，但本轮没有先问是否吃饭；还有“说到‘能有什么事’时”，本轮没有对应台词。这与自动删除整条重复台词的策略相容：`style-review.ts:100` 的 removeExactRepeatedLines 命中一句就删掉整条 dialogue 指令，不能保证剩余代词、回答和动作仍有前文。

无论具体删除发生在哪一次修复，这些是已提交正文中的断裂，不能只看 XML/指令格式正确就视为修复成功。应把上下句依赖和问答完整性纳入验收，避免删除台词后留下其回答。

### 6. 固定消息能触发，消息之后缺乏后续闭环

快速诊断 T5 结束 16:45 时死讯 pending，T6 至 17:05 变为 delivered，警方明确告知死亡、要求保持电话畅通并等待后续联系。直到午夜，剧情主要继续盯手机和被劝回家，没有兑现、取消或解释后续联络。

16:00 是程序阈值，跨过阈值后由下一个成功模型回合呈现；因此一次长时间跳跃加下一回合会延迟正文中的消息。这是当前离散回合设计的结果，不能误写成精确 16:00 已经通知。应在长行动中切出关键事件，或明确说明此前未接来电与回拨结果。

午夜 cycleCount 确实 1→2、时间回 08:00、认知保留，并明确旧约定/等候地点失效。桥接结构成立，但“你确实尝试了‘用户输入全文’”很像系统回执，应承接具体事件，而不是复述命令。

### 7. Writer 缺失具体时钟，白天可以写成隔天早晨

调查诊断 T15–19 实际处于 11:00–12:00，正文却依次安排“明天一早”登记、咖啡厅打烊、路灯亮起、今晚睡觉、关灯摸黑。T20 在实际 12:00→12:45 中完整演成次日晨起、早点摊、出门报案；cycleCount 始终仍为 1，完全没有发生午夜重置。

`turn-preparation.ts:197` 给 Director 的 gameStatus.time 是正确 UTC 时间瞬间，但未明确本地时段；`:206` 的 Writer presentationContext 没有 time/gameStatus。实际 T15–19 Writer 请求只有资源规则中的通用“08:00–18:30 白天”，没有当前日期钟点。T19 背景契约甚至正确为 home-day，但正文仍写黑夜。因此是时间上下文丢失、Director 纵容错误计划和审核没有守住跨日边界共同造成，并非单纯夜景素材选错。

### 8. 目的地匹配错误造成零分钟“成功回合”

调查 T5 在学校问“学校……接下来应该去哪里”，Director 计划二十分钟，最终却还是 08:43；选项诊断 T9 选择“离开便利店，前往对面商住楼找灯织”，前后地点都被定为 supermarket，09:54 不变。

`action-narrative-context.ts:34,76` 在整句任意处找到旅行动词后，用 DESTINATIONS.find 匹配任意处地点，不区分出发地和目的地。便利店顺序在灯织之前，于是错误拿起点作终点。`locations.ts:172` 同地点返回零成本；`useGameLoop.ts:434` 的空值合并保留显式 0，覆盖 Director 的正常耗时；`game-transaction.ts:75` 最终允许时间不动。

这种输入可以不断增长 history 而不推进日期，没有最终事务层的“成功剧情至少推进一分钟”保证。因此目前不存在可靠的全天回合数有限上界。应区分“仅在原地移动”的零成本与“已经完成一轮对白/调查”的耗时，不宜无条件把所有零成本改成固定旅行收费。

### 9. standard 对新增物证和旧事实冲突仍有漏检

调查诊断 T4 提交了“请假条、家长代请、大人字迹”；T22 提交“这个礼拜有几天没进校门”的具体考勤信息，T23 玩家继续据此追问。核对各轮最后有效 Writer/修复 packet，authorizedFacts 和新背景提案均无对应授权。T22 仅有已经知道的衣柜空缺。不是读错第一版 packet，也不是普通雨景润色。

T20 的报案陈述写“前天早上她出门，说去学校，之后没有回来”，与正式开局当天 06:50 的“今天不去学校”冲突。T4/T20/T22 的实际阶段日志没有 fact-review；T4/T22 虽调用 State，也没有阻止这些叙事事实进入后续历史。State 调用成功不能替代对正文中新事实的发现与校验。

这些是文风被放行后观察到的事实校验缺口，不能声称原版一定向玩家展示了同样内容。它们同时说明“只修文风就足够”不成立：下游必须能发现无授权的新物证，以及与正式开局相冲突的失踪时间线。

### 10. 核心死讯没有实际告知，却被标记已送达

调查诊断 T35 的 before 为 16:15、deathNews=pending，after 仍 16:15、deathNews=delivered。正文只说“有一件事需要当面跟你说——关于文穗的”“对方没有在电话里说，只重复了一遍地址”，没有告知死亡。文中的“死亡证明”指她的父母，不能算文穗死讯。

这一轮 Writer **确实收到了**“文穗的死讯必须在本回合送达玩家……理智应明显下降”的强提示，packet 的 b4/b5 也明确要求死亡告知与接讯反应。与缺时钟问题不同，这次是生成未服从已经下发的要求，而交易层没有检查实际演出。

`turn-preparation.ts:114` 记录 hadPendingDeathNews；`useGameLoop.ts:441` 在成功结算时直接将其作为 deliverPendingDeathNews；`game-transaction.ts:89` 只依据该布尔量与旧 pending 状态置 delivered，没有接收正文核验。`orchestrator.ts:508` 的正文事实审查条件也不包括死讯 pending；T35 实际没有 fact-review。随后 `scheduled-events.ts:29` 又告诉后续模型“玩家已得知文穗的死讯”，造成程序知道、玩家却没被告知。

之后 T36 跳过到所确认便直接回家整理材料，T37 再次演开门回家，给刚刚在场主动送行的灯织重新转发电话原话；16:20 还写出“午夜到了”，机制却没有过日。这把未完成事件、遗忘既有行动、错误时钟与段落重复叠加在了一起。

对应验收应要求事件交付有实际正文证据；仅有事件标记、导演计划或 State 调用均不够。快速诊断 T6 明确说“人已经死亡”是成功对照，不能将调查 T35 的漏播误说成每条路线必现。

人物评价以已提交诊断正文为主；原版失败草稿仅用于定位生成和审核问题，不当作玩家已经看到的剧情。

不是“人设完全崩了”，也不能判“人设保持良好”。姓名权限、职业、基础语气有局部可靠证据；跨回合记忆、人物差异化、已知背景权限和同一人物对不同玩家态度的持续响应尚不可靠。林静与赵刚自身姓名认知及深层关系未充分覆盖，不能说完整认识链都已通过。

选项诊断虽然最终过日，T53–55已提前连续宣告“时间越过午夜”，机制却分别才22:31、23:01、23:31；只有T56真正触发day-end。调查T31还用“现在下午店里只有两个人”否定陈慧慧所说的“早上人多”，制造了不成立的矛盾。剧情公平性需要核对人物陈述的具体时间，不能靠累积心虚动作维持悬疑。

## 回合数的机制边界

实际开局 08:00，到午夜有 960 分钟。普通对白提示通常 5–15 分钟，调查 20–40 分钟；缺省 10 分钟，明确时间请求可至 180 分钟。仅按平均推进计算：10 分钟需 96 回合，25 分钟需 39 回合，40 分钟需 24 回合，120 分钟需 8 回合，180 分钟需 6 回合。这是算术，不是实测成功区间。

实际还会遇到零分钟回合、旅行成本覆盖导演时间、重试不推进、资源提前耗尽、剧情结束、空场景推进以及固定事件插入。没有固定“每一天 N 回合”约束，因此不能给没有前提的有限上界。即使长时间输入，导演也可在有事件时缩短动作；快速实测因此是十次提交，而不是八次。

后续优化应先恢复可用性和结算一致性，再依据明确的体验目标设计第一天长度。增加 token 预算或换更大模型，都不能直接解决空场景提交、状态调度遗漏和旧文证据不核验。

## 修复优先级与验收方式

1. **先禁止空正文提交**：场景与音乐都合法但无台词、正文藏进 observe、字面量换行、嵌套标签等真实失败样本进入回归集。拒绝时 history、时钟、资源、已知事实均不变化；不能只有解析函数返回对象的测试。
2. **统一开局事实与实际已读历史**：开局正文和可选观察分开投影，已经揭示的事实从第一轮就进入统一账本；语义审核必须收到授权豁免。拒绝旧文复读需提供可在旧文核验的引句，不能接受候选冒充旧文的理由。
3. **明确时间与移动契约**：Director、Writer、审核与预规划都收到同一个本地日期、时刻、时段、cycleCount。中午不得写成已过夜，除非本轮确实扣除了相应时长并经过重置。用“离开 A 前往 B”“在 A 问去哪里”等真实句式验证目的地，不让起点抢占匹配。
4. **补足 standard 状态覆盖**：普通自由搜索、正文地点变更、死讯、长期等待与显著资源行为也必须由明确规则或 State 负责结算。避免为节省一次调用而让整天资源冻结；同时不必对纯重复菜单展示乱扣费用。
5. **查找正文新增事实，而非只审计划已有事实**：用无授权的考勤记录、请假条字迹、既往伤口/品牌偏好和“前天失踪”冲突作为实际漏检样本。事实审核与 State 都通过仍须阻止不应进入世界记忆的内容。
6. **把推进目标交给规划，而不是让文风审核索要新线索**：记录本轮完成了什么、失败的具体原因、下一步与上一轮有何不同；第一天可以不增确认级线索，但不能反复重新决定出门。NPC 人物档案按实际场景覆盖，不只依赖 Director 恰好列出 speakerIds。
7. **修复后检查问答与动作引用**：删重复内容必须连同依赖的回答/动作一起重写。用“你说吃过了”“她说到第三条时”等断链样本验收，避免格式修复制造新的阅读问题。
8. **最后重新做速度优化**：固定同样开局、连续历史与输入策略，分别测原版 standard/strict 的完整日。分别报告 API 首 token、有效正文可播、失败等待、后台成本、真实日终完成率、文字量与推进比例，不能仅以 mock 单元测试通过或一次新聊天首回合变快作为验收。

本报告没有擅自选定一天应压到多少回合。要调整体验长度，应先约定目标阅读时长及调查密度，再调分钟、单回合字数和剧情进度，不能仅把导演 timeCost 放大来让数字更好看。

## 结论边界

本轮只评估首个重复日与第一次日终；文穗本人、后续日循环、第三到第四天门槛、所有结局和 strict 连续全天尚未覆盖。草稿发现与已提交问题在证据中分开。诊断放行不能证明生产稳定，API 成功和 Vitest 通过也不能证明剧情合格。测试收集器的断言只保证采集了尝试记录，具体完成状态必须查看 stopReason 与可播放台词。

本轮未修改生产代码、未部署任何文风放行方案；新文件只有测试、分析和评估材料。上一轮独立单回合延迟结果仍可作为那种测试条件的数据，但不能外推成带正式开局的连续游戏体验，本轮应作为更严格的补充证据。
